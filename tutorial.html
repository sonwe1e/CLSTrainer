02 / 整体架构

数据从哪来，决策从哪出

CLSTrainer 是一个双帧二分类框架：输入两张连续帧，输出"是否发生跳变"。核心理念是训练与部署共用同一个 decision.threshold，保证阈值不漂移。

数据层

PNG 文件或 packed uint8 分片，经 DataLoader 解码为 [B,2,3,H,W] uint8 张量

→
模型层

用户提供的 model.factory 函数构建模型；输入两帧，输出 [B,2] logits

→
损失层

CE + 阈值间隔损失 + 可选 OHEM / ranking；均在 src/game_cls/losses/threshold_loss.py

评估层

全局 / 最差游戏 / 亚型 FPR-recall 矩阵；固定阈值 decision.threshold

→
选模层

constrained 模式：先按 FPR/recall 合格性过滤，再按三元键排序

→
导出层

PyTorch 权重 / ONNX + export_manifest.json（含阈值、形状）；release gate 拦截未达标模型

单一阈值原则：decision.threshold（默认 0.99）是训练损失、评估器与导出 manifest 的唯一来源。不要在不同环节分别设置阈值。
03 / 快速上手

三步跑通第一次训练

以下命令基于合成数据，不需要真实模型或数据集，用来验证环境和工具链。

  1. 安装

    shell
    python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
python -m pip install -e ".[dev]"                    # 含 torch(cpu) + pytest

  2. 预检环境

    shell
    cls-trainer doctor --config configs/recipes/example_debug.yaml

    doctor 会验证：配置 schema、模型 factory 是否可导入、checkpoint 是否存在、数据索引是否合法。未通过时直接报错，不进入训练。

  3. 最小训练（2 步）

    shell
    cls-trainer train --config configs/recipes/example_debug.yaml train.max_steps=2

    每次启动都会在 experiment.output_dir 下分配一个不可覆盖的 Run 目录。结束时打印 run dir、best ckpt 路径。

注意：example_debug.yaml 使用合成数据和玩具模型。生产训练必须设置真实的 model.factory、model.checkpoint_path 和数据索引路径，否则 doctor 会拒绝启动。
04 / 数据准备

从原始帧到训练索引

数据路径需满足 <split>/<game>/<0|1>/<video_id><frame_id>.png，文件名格式 ^\d{7}\.png$。

典型数据准备流程
# 1. 从 train_all 目录自动做源视频级划分（不按帧划分，防止同视频帧跨 split）
cls-trainer dataset prepare \
  --config configs/recipes/game_cls_production.yaml \
  --train-root /data/train_all --test-root /data/test --val-ratio 0.10

# 2. 审计：SHA-256 内容哈希 + 跨 split 泄漏检测
cls-trainer dataset audit --config configs/recipes/game_cls_production.yaml

# 3. （可选）打包为 packed_uint8 以消除 PNG 解码开销
cls-trainer dataset pack --config configs/recipes/game_cls_production.yaml \
  --output-dir /data/packed/

划分的可复现性

划分基于 源视频 UID 而非帧，用持久化 manifest（SHA-256 哈希）保证重复运行结果一致。data.require_content_hash_audit=true 强制要求内容哈希审计，防止同内容异标签和跨 split 泄漏。

PNG vs packed_uint8

默认 PNG（Pillow 解码）；当 host_data_wait 高且 PNG 解码成为瓶颈时，考虑切换 data.backend: packed_uint8。切换前后必须在同台服务器上保持 batch、worker、步数一致做 A/B 对比，不保证所有环境都更快。

05 / 训练与评估

一次训练的生命周期

了解三种评估角色和选模合约，有助于判断训练是否健康、何时应该介入。

三种评估角色

角色触发条件用途
train_probe每 train_probe_every_steps 步在固定 train 子集上评估（无增强），计算泛化差距
val_quick每 val_quick_every_steps 步轻量 validation，提供趋势反馈；不触发选模
val_full每 val_full_every_steps 步完整 validation，驱动模型选择和 early stopping

test split 在训练结束后只评估一次（cls-trainer evaluate --split test），绝不参与选模。

constrained 选模合约

只有同时满足以下条件的 checkpoint 才视为合格（eligible）：

  • global_fpr ≤ max_global_fpr（默认 0.01）
  • worst_game_fpr ≤ max_worst_game_fpr（默认 0.02）
  • positive_recall ≥ min_positive_recall（默认 0.8）

合格模型按 三元键 排序：
(global_recall, worst_game_recall, −negative_score_p999)

不合格的 checkpoint 进入 top-k 注册表但永远排在合格模型之后。早停遵循相同合约。

关键输出文件

文件内容
checkpoints/model_best_selection.pth选模最优权重（纯 state_dict，直接用于推理）
checkpoints/checkpoint_best_selection.pth选模最优完整 checkpoint（含 optimizer / RNG，用于 resume）
metrics/evaluation.jsonl全部评估历史：时序指标 + 泛化差距
reports/val_full_step_XXXXXXXX/metrics.json单次 full validation 的详细指标
benchmarks/<run>_<alias>/report.jsonbenchmark evaluate 的 gate 结果

7.1 更换或扩展损失函数

所有损失逻辑在一个文件中：src/game_cls/losses/threshold_loss.py。训练循环的入口是：

src/game_cls/engine/training/loop.py（节选）
loss, components = combined_loss(
    logits, labels, config["loss"], global_step, total_steps
)

当前损失组成：

组件控制键默认权重说明
交叉熵（CE）loss.cross_entropy_weight1.0标准分类损失，支持 label_smoothing
阈值间隔损失loss.threshold_loss_weight0.20在 decision_threshold 附近施加额外 margin，训练初期线性升温
负样本尾部 OHEMloss.negative_tail_loss_weight0.0（禁用）只惩罚最难的负样本，可设 negative_tail_hard_negative_k 限制数量
Pairwise rankingloss.rank_loss_weight0.0（禁用）要求正样本 logit 高于负样本 rank_margin

添加新损失组件（以 Focal Loss 为例）：

步骤 1：在 threshold_loss.py 实现函数
def focal_loss(logits, target, *, gamma: float = 2.0) -> "torch.Tensor":
    import torch.nn.functional as F, torch
    ce = F.cross_entropy(logits.float(), target, reduction="none")
    pt = torch.exp(-ce)
    return ((1 - pt) ** gamma * ce).mean()
步骤 2：在 config_schema.py 的 loss 块注册键（约第 517 行）
"focal_loss_weight": _k("float", "Weight of focal loss; 0 disables."),
"focal_gamma":       _k("float", "Focal loss gamma exponent."),
步骤 3：在 combined_loss() 中接入
focal_w = float(config.get("focal_loss_weight", 0.0))
if focal_w > 0:
    total = total + focal_w * focal_loss(logits, target, gamma=config.get("focal_gamma", 2.0))
步骤 4：在 YAML 中启用
loss:
  cross_entropy_weight: 0.0   # 如果 focal 完全替代 CE 则设为 0
  focal_loss_weight: 1.0
  focal_gamma: 2.0

7.2 更改图像加载方式

图像加载由 data.backend 配置。后端分发逻辑在 src/game_cls/engine/training/loaders.py 的 _build_real_data_components()（约第 155 行）。

png（默认）

使用 Pillow 解码（Image.open(path).convert("RGB")），再通过 torchvision 转为 [C,H,W] uint8 tensor。路径字符串存储在索引中。

适合数据量小或存储速度足够快的场景；无需预处理。

packed_uint8

帧以 CHW uint8 字节直接写入 .bin 分片，通过 numpy.memmap 零拷贝读取，免去 PNG 解码。PackedUint8Backend 在 src/game_cls/data/packed_backend.py。

需要先用 cls-trainer dataset pack 预处理数据，并配置 data.train_packed_index 等路径。

添加自定义后端：

7.3 接入自定义模型与配置权重加载

model.factory 是框架的模型接入点。工厂函数通过 module:function 格式动态导入，在训练启动时被调用一次。

工厂函数接口约束
# 你的工厂函数签名（示例）
def build_my_model(
    width: int,
    height: int,
    channels: int,
    checkpoint_path: str | None,
    **kwargs,          # 接收 model.kwargs 中的所有额外参数
) -> torch.nn.Module:
    model = MyModel(...)
    if checkpoint_path:
        state = torch.load(checkpoint_path, map_location="cpu", weights_only=True)
        model.load_state_dict(state, strict=False)
    return model
在 YAML 中配置工厂和权重路径
model:
  factory: "my_package.models:build_my_model"
  checkpoint_path: /path/to/pretrained_backbone.pth
  trainable_rules:
    cls_head:
      pattern: "^cls\\."
      lr_scale: 1.0
      unfreeze_at_step: 0
      priority: 10
  kwargs:
    cls_dropout: 0.1               # 传给工厂的额外参数

分阶段解冻（trainable_rules）：这是唯一的可训练参数定义，支持按 step 逐步解冻、为不同参数组设置独立学习率缩放。

分阶段解冻配置示例
model:
  trainable_rules:
    cls_head:
      pattern: "^cls\\."           # 正则：step 0 起训练分类头
      unfreeze_at_step: 0
      lr_scale: 1.0
      priority: 10
    backbone_stage4:
      pattern: "^backbone\\.stage4\\."  # step 500 起解冻 stage4
      unfreeze_at_step: 500
      lr_scale: 0.1                # 该参数组的学习率 = base_lr × 0.1
      priority: 5
    backbone_stage3:
      pattern: "^backbone\\.stage3\\."
      unfreeze_at_step: 2000
      lr_scale: 0.01
      priority: 1
规则 fingerprint：命名规则集合会被哈希存入 checkpoint。resume 时若规则发生变动，训练立即报错，防止谱系污染。如需调整规则，应用 --fork 而非 --resume。
严格加载验证：框架会检查所有被冻结的非 cls 参数均来自 checkpoint_path 而非随机初始化。若 checkpoint 缺少某个非 cls 参数，训练启动时报错，不允许静默降级。

7.4 自定义数据增强

增强逻辑集中在 src/game_cls/data/augment.py 的 ConsistentPairAugment 类。接口约束：输入 [2, C, H, W] uint8 tensor（帧对），输出相同形状；两帧的随机参数必须共享同一次抽样——模型比对帧间差异，独立抽样会引入虚假信号。

RNG 约束：每个 transform 必须先抽取一次随机值，再将相同值应用于两帧，而非对两帧独立抽样。loaders.py 在调用前会 fork 并 seed RNG（基于 request.augmentation_seed），保证多进程确定性。
步骤 1：在 augment.py 实现 pair-transform 类
class _MyContrastPair:
    """对比度增强：两帧使用相同系数。"""
    def __init__(self, cfg: dict):
        self._lo = cfg.get("contrast_lo", 0.8)
        self._hi = cfg.get("contrast_hi", 1.2)

    def __call__(self, pair: "torch.Tensor") -> "torch.Tensor":
        # pair: [2, C, H, W] uint8 — 单次抽样，两帧共用
        factor = random.uniform(self._lo, self._hi)
        out = torch.clamp(128 + factor * (pair.float() - 128), 0, 255)
        return out.to(torch.uint8)
步骤 2：在 ConsistentPairAugment.__init__ 末尾接入
# augment.py — ConsistentPairAugment.__init__ 末尾追加
if config.get("my_contrast", {}).get("enabled", False):
    self._transforms.append(_MyContrastPair(config["my_contrast"]))
步骤 3：在 config_schema.py 注册子块
# SCHEMA["augmentation"] 中追加：
"my_contrast": {
    "enabled":     _k("bool",  "Enable custom contrast augment."),
    "contrast_lo": _k("float", "Lower bound of contrast factor."),
    "contrast_hi": _k("float", "Upper bound of contrast factor."),
},
# _DEFAULT_AUGMENTATION 中追加：
"my_contrast": {"enabled": False, "contrast_lo": 0.8, "contrast_hi": 1.2},
步骤 4：在 YAML 中启用
augmentation:
  my_contrast:
    enabled: true
    contrast_lo: 0.75
    contrast_hi: 1.3

现有 augmentation presets（configs/presets/augmentation/）：none、light、standard。新 preset 只需新建一个 YAML 文件；评估集和 probe 集不接受 transform，无需额外保护。

09 / 常见问题

容易踩的坑

这些问题通常决定一次训练只是"能运行"，还是"结果可信"。

为什么 0.99 分数不等于 99% 真实概率？
训练采样把类别调整为约 50/50，加上阈值间隔损失改变了自然先验。0.99 应记录为业务分数而非概率；需要概率解释时，应在自然分布 calibration 集上重新校准。
train / validation / test 三者的区别是什么？

train：只参与梯度更新。

validation：参与曲线、模型选择和 early stopping；可以多次评估。

test：训练结束后只评估一次（cls-trainer evaluate --split test），绝不参与选模。若没有独立 test 集，--split test 会被拒绝（退出码 3）。

validation 索引必须显式配置；test 索引仅供训练结束后的独立评估使用。

early stopping 会不会太早停止？
只在 full_validation 上判断；burn_in_steps（默认 6000）之前不停止；连续 patience_evaluations（默认 3）次未改善才停止。停止后自动恢复最佳权重（early_stopping.restore_best=true）。状态写入 checkpoint，resume 后不重算 patience。
为什么 NPU 利用率低，但 train_only_samples/s 很高？
train_only_samples/s 反映主线程提交 kernel 的速率，NPU 默认异步执行。应同时查看 wall_samples/s、host_data_wait 和 NPU utilization。host_data_wait 高说明数据加载是瓶颈，此时增加 worker 数或切换 packed 后端更有效。
什么时候应该切换 packed_uint8？
当同机实测表明 PNG 解码、CPU 或小文件随机读取限制 NPU 利用率时。切换前后必须保持模型、batch、worker、增强和步数一致，比较稳定区间吞吐和 host_data_wait。packed 不是无条件更快——随机 shard 访问、page cache 和存储位置都会影响结果。
resume 和 fork 有什么区别？

--resume <run目录>：精确继续同一个 Run，step、sampler、RNG、early stopping 状态完全恢复，输出写入同一目录。

--fork <run目录>：以某个 Run 的配置为起点开始全新的 Run，分配新目录，不继承训练状态。适合在收敛点基础上用不同 lr 或 loss 权重继续实验。

为什么 trainable_rules 必须准确匹配参数？
过宽的正则会把主干参数意外纳入训练，过窄则可能得到 0 个可训练参数。规则必须非空，学习率缩放必须为正数；doctor 和训练启动都会打印最终可训练参数集合。
