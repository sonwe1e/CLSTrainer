Production handbook · dual-frame classification

从百万帧数据到可验证的 NPU 训练

CLSTrainer 是面向多游戏、双帧二分类任务的生产训练框架。它不是“把模型塞进训练循环”的薄封装， 而是把数据审计、懒采样、冻结主干校验、单卡/八卡训练、部署阈值评估、错例报告和精确恢复组成一条可验收的链路。

01 / OVERVIEW

30 秒理解这个项目

先明确项目边界。CLSTrainer 针对固定的双帧、多游戏、二分类业务做深度工程化；它不是自动适配任意模型、任意尺寸和任意任务的通用 Trainer。

它是什么

一条可审计、可恢复、可部署的训练链路

  • 输入两张连续画面，学习帧间变化而非仅靠静态纹理。
  • 支持多游戏数据平衡，防止大游戏样本淹没小数据游戏。
  • 支持 CPU/CUDA 调试、Ascend 单卡与 HCCL 八卡训练。
  • 固定以第二类 Softmax 分数严格大于 0.99 作为业务判定。
它不是什么

不是无约束的通用分类框架

  • 不会自动 resize、自动交换宽高或猜测模型输入格式。
  • 不会用 strict=False 悄悄忽略冻结主干缺失。
  • 不会把参与选模的 validation 当作无偏测试集；test 只在训练结束后评估一次。
  • 不会保证 packed 在所有存储和采样模式下都一定更快。
IN

输入契约

每个 batch 形状为 [B,2,3,208,448]，两帧执行一致的数据增强。

OUT

输出契约

模型必须返回 [B,2] logits；框架直接拒绝其他输出形状。

CLS

训练契约

默认只训练名称包含小写 cls 的参数，其余主干被冻结。

99

部署契约

softmax(logits)[:,1] > 0.99 才判为正类；0.99 是业务分数，不等同于真实概率。

02 / WHY CLSTRAINER

项目做了什么，为什么值得使用

项目的价值不在某个单独模块，而在于把“普通训练脚本容易静默出错的地方”全部变成显式契约、报告或停止条件。

维度普通训练脚本CLSTrainer 的技术路线直接收益
百万帧数据预生成所有 pair 或每次递归扫描Frame/Video Parquet + batch 时懒生成 PairRequest内存随视频索引增长，而不是随全部 pair 数增长
数据正确性文件能打开就训练尺寸、命名、目录、重复内容、跨 split 泄漏与 delta 覆盖审计在训练前发现错误标注、失效数据和评估污染
多游戏平衡全局随机抽样delta → game → label → video 分层采样，支持 game_alpha控制大游戏与小游戏的训练权重
多卡一致性各 rank 独立随机抽样确定性全局 batch，再按 rank 切片避免多卡重复、便于复现和精确恢复
预训练主干strict=False 后继续所有非 cls 参数和 buffer 必须 100% 加载避免随机初始化且被冻结的主干被误当作预训练模型
NPU DataLoader沿用 Linux 默认 forkNPU 多 worker 强制 spawn、180 秒 timeout、train/eval worker 分离避免 NPU runtime 初始化后的 worker 静默死锁
评估只看全局 accuracy/F1global、macro-game、worst-game、video、AUC、Brier、ECE、margin 分位数，以及 train probe vs validation 的泛化差距发现小游戏、特定标签或特定视频的退化，并区分过拟合与置信度漂移
错例内存收集或手工挑选分 rank 流式 Parquet + 合并 + HTML preview大规模 full test 不需要在 rank 0 保存百万 Python 对象
恢复模型 + optimizerscheduler、scaler、sampler 位置、各 rank RNG 与基础权重哈希中断后从同一采样位置继续，而不是近似恢复
部署产物训练 checkpoint 与模型权重混杂纯 state_dict 与完整 checkpoint 分离部署侧无需加载 optimizer、sampler 或训练状态

05 / MODEL INTEGRATION

如何接入你的真实模型

模型接入最容易出现模块路径、forward 接口、cls 命名和 checkpoint key 不一致。下面给出仓库内可以直接采用的适配器形式。

FILE LOCATION

建议目录

project tree
src/game_cls/
├── __init__.py
└── model/
    ├── __init__.py
    ├── builder.py
    └── my_classifier.py

创建文件后执行 python -m pip install -e .，确保当前环境导入的是这个仓库。

MODEL CONTRACT

框架要求

FACTORY
package.module:function，框架调用 factory(config)
FORWARD
forward(image0, image1)，两者均为 [B,3,208,448]
OUTPUT
必须是 [B,2] logits
TRAINABLE
需要训练的参数名必须包含小写 cls
DEVICE
factory 只构建 CPU 模型，不调用 .npu()、DDP 或 set_device
src/game_cls/model/my_classifier.py
from __future__ import annotations

from typing import Any

import torch
from torch import nn


class MyDualFrameClassifier(nn.Module):
    def __init__(self, num_classes: int = 2) -> None:
        super().__init__()
        self.backbone = build_your_backbone()

        # 所有需要训练的分类相关参数都使用小写 cls 命名。
        self.cls = nn.Linear(self.backbone.output_dim, num_classes)

    def forward(
        self,
        image0: torch.Tensor,
        image1: torch.Tensor,
    ) -> torch.Tensor:
        # image0 / image1: [B,3,208,448]
        features = self.backbone(image0, image1)
        logits = self.cls(features)
        return logits  # [B,2]


def build_model(config: dict[str, Any]) -> nn.Module:
    return MyDualFrameClassifier(
        num_classes=int(config.get("num_classes", 2)),
    )

验证双帧接口

python

!
冻结主干检查是生产保护，不应随意关闭
如果出现 missing_non_cls 或 shape_mismatch_non_cls，说明当前模型结构与 checkpoint 不一致。应换正确权重、转换 key、重命名真实分类头，或把可重建缓存设为 non-persistent；不要通过关闭检查掩盖随机冻结参数。
错误最常见原因正确处理
ModuleNotFoundErrorfactory 模块路径不存在、目录写成 models/model 错误或项目未 editable install放入 src/game_cls/model/，检查 __init__.py 并执行 pip install -e .
missing_non_cls当前冻结主干存在 checkpoint 没有的参数或 buffer确认它属于 backbone、cls 还是可重建 buffer，再对齐模型和权重
shape_mismatch_non_cls权重来自不同模型版本或结构配置使用完全匹配的基础 checkpoint，不要跳过 shape mismatch
没有可训练参数分类头名称不含小写 cls将真实分类模块命名为 cls、cls_head 等
设备不匹配factory 或模型构造阶段自行调用 NPUfactory 返回 CPU 模型，由 trainer 统一绑定设备和 DDP

配置如何继承、覆盖和生效

绝大多数运行问题都应先查看最终生效配置。项目支持 YAML base 继承和命令行 dotted-key override；后者优先级最高。

BASE

npu_production.yaml

真实数据、模型、loss、dataloader、evaluation 和 checkpoint 的生产默认值。

1P PROFILE

继承生产配置，保持单进程单设备运行。

8P PROFILE

RULE 1

命令行覆盖使用 dotted key

examples

model.checkpoint_path=/abs/model.pth
data.backend=packed_uint8

值由 YAML 解析，因此 true、false、null、数字和行内字典都会转换成对应类型。

RULE 2

角色级 DataLoader 配置优先

important
# 生产配置已有 train/eval 子项时，这个旧写法不能覆盖它们：
dataloader.num_workers=0

# 正确关闭所有 worker：
dataloader.train.num_workers=0
dataloader.eval.num_workers=0
RESOLVED CONFIG

永远检查最终生效配置

每次训练会把完整配置写入运行目录：

path
runs/<RUN_NAME>/resolved_config.json

排查 batch、worker、评估周期、factory 或 checkpoint 问题时，优先读取该文件，而不是只看原始 YAML。

PROFILE VS OVERRIDE

什么时候改 YAML，什么时候用 CLI

  • 长期稳定默认值：写入配置文件。
  • 短期 smoke、A/B 和诊断：使用命令行 override。
  • 新数据后端或设备模式：建立新的 base profile。
  • 不要把一次临时调试参数直接变成生产默认值。

      08 / LOGS & EVALUATION

      如何读训练日志和评估报告

      训练是否“在跑”不等于训练是否“高效”或“可信”。日志用于定位数据、主机提交和评估开销；报告用于判断全局与各游戏的业务表现。

      example training log
      step=200/10000 loss=0.265080 ce=0.217867 threshold_loss=0.042100 \
threshold_weight=0.2000 accuracy=0.8740 \
interval_samples/s=2650.23 interval_step_time=0.0377s \
data_wait_ratio=37.6% learning_rate=8.6e-05 grad_norm=0.2841 \
evaluation_seconds=0.000 checkpoint_seconds=0.000 wall_samples/s=53.30 \
host_enqueue_timing={'host_data_wait': 0.998, 'host_h2d_enqueue': 0.0077,
'host_forward_enqueue': 0.0053, 'host_backward_enqueue': 0.0038,
'host_optimizer_enqueue': 0.0024}
      loss / ce / threshold_loss区间内按样本加权的平均损失（多卡下在 rank 间 all-reduce），曲线不再被单个 batch 噪声主导；原始 last-batch 值仍写入 train_metrics.jsonl 的 loss/ce/threshold_loss 字段。
      accuracy / recall / specificity区间内 0.99 阈值下的训练集 accuracy、正类 recall 与负类 specificity（interval_* 字段）。
      threshold_weight经过 warmup/ramp 后的当前阈值损失权重。
      interval_samples/s日志区间样本吞吐；wall_samples/s 是从运行开始累计的端到端吞吐，受冷启动和评估影响。
      host_data_wait主进程等待下一批数据的时间；明显高于其他字段时输入流水线是瓶颈。
      TRAIN PROBE

      同口径泛化对照

      固定、无增强的 train 子集，与 validation 使用完全相同的 evaluator；train probe 与 validation 的 CE/selection 差距就是泛化间隙。

      VALIDATION

      趋势观察与选模

      val_quick 每个视频均匀抽样做高频趋势监控；val_full 枚举全部合法 pair、流式写错例并参与 best 模型选择与 early stopping。

      TEST

      训练后的唯一一次评估

      训练循环内永不评估 test；训练结束后用 cls-trainer evaluate --split test 只评估一次，绝不参与选模。

      组合选模配置

      evaluation
      evaluation:
  selection_metric: composite
  selection_weights:
    global_f1: 0.40
    macro_game_f1: 0.40
    worst_game_f1: 0.20
  minimum_worst_game_f1: null

      先完成可靠基线，再根据真实分布设置非零 worst-game floor，不要凭空猜门槛。

      指标应该如何解释

      • global F1：总体业务效果，但可能被大游戏主导。
      • macro-game F1：每个游戏等权，更能反映跨游戏稳定性。
      • worst-game F1：最弱游戏的底线，适合建立上线 guardrail。
      • FP/FN by game-label：定位误报和漏报来自哪些游戏。
      • Brier / ECE / margin 分位数：观察分数校准与阈值附近分离程度；0.99 仍是业务分数而非自然概率。
      • train probe vs validation：同口径下 probe CE 继续下降而 validation CE 上升，就是泛化退化；固定 0.99 阈值 F1 变差但 PR-AUC 基本不变时，更可能是置信度漂移。
      • validation：参与选模与 early stopping；对外无偏结果必须来自从未参与选模的独立 test（cls-trainer evaluate --split test）。
      ◆
      同一步同时命中 val_quick 和 val_full 时只运行 val_full
      smoke 时可关闭 val_full_at_end 以缩短验证；正式训练结束时应保留 final full validation，确保最后模型参与比较。test 永远不进入训练循环。每次评估追加一行到 metrics/evaluation.jsonl，train probe 与 val_full 同一步时额外记录 generalization_ce_gap / generalization_score_gap；overview.html 的六类曲线和关键 step 标记（best selection、best val loss、泛化退化起点、early-stop）都由它驱动。

      DATA PIPELINE PERFORMANCE

      PNG 与 packed 的正确比较方式

      指标含义如何比较判断
      host_data_wait主线程等待下一批数据相同 batch、增强、步数和 worker明显高于其他主机字段时数据受限
      wall_samples/s累计端到端吞吐忽略冷启动，比较后半段区间不能只看最后一个累计值
      NPU utilization设备是否持续工作排除评估和 checkpoint 窗口锯齿且 host_data_wait 高表示输入饥饿
      CPU / iowaitPNG 解码或存储瓶颈worker=2→4→8 逐级 A/B提升不足 15% 时停止继续加 worker
      worker RSS多进程和 memmap 内存成本访问多个 shard 后观察防止八卡放大后主机内存过高
      ◆
      packed 是候选高吞吐后端，不是无条件更快
      它消除训练热路径中的 PNG 解码，但随机 shard、page cache、存储位置和增强仍会影响结果。必须在同一台服务器上保持模型、batch、worker 和步数一致后 A/B。

      12 / FAQ

      常见认知错误

      这些问题通常决定一次训练只是“能运行”，还是“结果可信”。

      为什么 0.99 不能直接称为 99% 真实概率？
      训练采样把类别调整为约 50/50，并加入阈值间隔损失，改变了自然先验。当前 0.99 应记录为业务分数；需要概率解释时，应在自然分布 calibration 集上重新校准。
      train / validation / test 三者有什么区别？
      train 只用于梯度更新；validation 用于曲线、模型选择和 early stopping；test 在训练结束后只评估一次，绝不参与选模。旧配置的 quick_test_*/full_test_* 会自动迁移为 val_quick_*/val_full_*；没有 val_index 时 test 会临时充当 validation 并给出明确警告。独立 test 通过 cls-trainer evaluate --split test 评估。
      如何判断约 10,000 step 附近是过拟合还是置信度漂移？
      同一 eval 口径下对比 train probe 与 validation：train probe CE 继续下降而 validation CE 上升，说明泛化退化；若固定 0.99 阈值 F1 变差但 PR-AUC 基本不变，则更可能是置信度漂移。overview.html 用 generalization gap 曲线和 best/退化/early-stop 标记辅助判断。
      early stopping 会不会把训练提前掐断？
      只在 full validation 上判断，burn-in 之前不停止，连续 patience 次未改善才停止并恢复最佳权重；max_steps 仍是安全上限。状态（best_value、best_step、bad_evaluation_count、stop_reason）写入 checkpoint，恢复训练不会重算 patience。
      为什么 train_only_samples/s 很高，但 NPU 利用率仍然低？
      该指标主要反映 batch 返回后主机提交调用的速率，NPU 默认异步执行；它不是设备同步后的真实吞吐。应同时查看 wall_samples/s、host_data_wait 和 NPU utilization。
      为什么不能直接把 DataLoader timeout 调到很大？
      timeout 的目的在于把 worker 死锁或读取异常转成明确失败。首 batch 卡住时应先用 num_workers=0、1、2 分阶段定位，而不是把 180 秒改成 1800 秒继续等待。
      什么时候应该使用 packed_uint8？
      当同机实测表明 PNG 解码、CPU 或小文件随机读取限制 NPU 利用率时。切换前后应保持模型、batch、worker、增强和训练步数一致，比较稳定区间吞吐和 data wait。
      为什么只训练名称包含 cls 的参数？
      这是当前任务的冻结策略，用完整预训练主干只更新分类模块。严格加载检查确保所有被冻结的非 cls 参数和 buffer 都来自基础 checkpoint，而不是随机初始化。
      Reliable before scalable

      先证明链路可靠，再让八张卡长时间工作

      推荐顺序是：数据契约 → 索引与审计 → 模型和 checkpoint 校验 → 2-step 基线 → 1P smoke → probe/validation → 独立 test 评估 → 恢复 → PNG/packed A/B → 8P smoke → 正式训练。
